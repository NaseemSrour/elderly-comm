Elderly Visual Communication Tablet App
1. ROLE AND OBJECTIVE
You are an expert Flutter engineer, UX designer specializing in accessibility and elderly users, product architect, and interaction designer.
Build a single-device Flutter tablet application designed for an elderly person who has essentially no experience with computers, smartphones, tablets, apps, buttons, menus, or technology.
The application is intended to help the elderly person communicate with a foreign caregiver/worker living in their home when the two people do not speak the same language.
The elderly user should be able to communicate requests such as:
• Bring me a bowl.
• Bring me water.
• Bring me a plate.
• Bring me a knife.
• Bring me bread.
• Put this in the refrigerator.
• Open the window.
• Close the window.
• Turn something on/off.
• Take something away.
• Wash something.
• Help me go to the bathroom.
• Help me sit down.
• Help me get into bed.
• Help me with something.
• Perform a morning routine.
• Perform a nighttime routine.
• And essentially any other household necessity that can be represented through configurable objects, actions, situations, and routines.
The central design principle is:
The elderly person should not have to understand technology, language, menus, keyboards, or sentence construction. They should only need to recognize familiar pictures and tap them.
This is NOT primarily a translation app.
It is a visual, semantic communication system.
The app should represent the elderly person's intent internally as structured semantic data, and only at the final presentation stage turn that intent into text, speech, and/or visual representation in the caregiver's language.

───

2. VERY IMPORTANT PRODUCT PHILOSOPHY
Do NOT build this as:
• a simplified Google Translate
• a normal chat application
• a normal Android tablet application
• a generic accessibility UI
• a conventional menu-driven application
• a keyboard-based communication system
• a sentence-writing application
Instead, think of it as:
A personalized visual communication board for one particular household.
The application should be customized around the actual elderly person's home, vocabulary, objects, routines, habits, and way of thinking.
The goal is not to support thousands of generic objects.
The goal is to support the approximately 30–100 things and requests that the particular elderly person actually needs.

───

3. THERE IS ONLY ONE APP
There is NO caregiver app.
There is NO required caregiver account.
There is NO requirement for the caregiver to install anything.
The elderly person's tablet is the communication device.
The elderly person constructs a request and the tablet displays the result.
The elderly person then physically turns the tablet toward the caregiver.
The caregiver reads the request from the tablet.
Optionally, the tablet can pronounce the request aloud in the caregiver's language.
Example:
The elderly person taps:
1. Kitchen
2. Bowl
3. Bring
4. To me
The app generates:
🥣
جيبلّي زبدية
 Bring me a bowl.
The elderly person shows the screen to the caregiver.
The caregiver does not need to interact with the application.

───

4. PRIMARY UX PRINCIPLE
The UI must be designed for someone who may not understand concepts such as:
• "tap"
• "button"
• "menu"
• "screen"
• "back"
• "settings"
• "swipe"
• "scroll"
• "app"
• "keyboard"
Therefore:
Never rely on the user understanding technology.
The UI should communicate through:
• large photographs
• large icons
• color
• spatial consistency
• repetition
• extremely simple choices
• immediate visual feedback
• familiar household objects
• minimal text
The user should recognize what they want rather than read instructions about what to do.

───

5. DO NOT OVERUSE TEXT
Text is allowed, but it is secondary.
A large photograph/icon should communicate the meaning first.
For example, instead of a small button:
Kitchen
prefer a huge visual card:
🍳
KITCHEN
Or, ideally, a photograph of the actual kitchen if appropriate.
For objects, use photographs of the actual household objects whenever possible.
For example:
• photograph of the actual bowl
• photograph of the actual cup
• photograph of the actual medicine
• photograph of the actual AC remote
• photograph of the actual window
• photograph of the actual kettle
The elderly person should think:
"That's my bowl."
rather than:
"I think that icon means bowl."

8. SEMANTIC / INTENT ARCHITECTURE
This is one of the most important architectural requirements.
DO NOT store communication primarily as sentences.
Represent requests as structured intents.
For example:
json
{
  "object": "bowl_01",
  "action": "BRING",
  "destination": "TO_ME",
  "quantity": 1
}

Another:
json
{
  "object": "bedroom_window",
  "action": "CLOSE"
}

Another:
json
{
  "object": "bread",
  "action": "BRING",
  "destination": "TO_ME",
  "quantity": 1
}

Another:
json
{
  "object": "bowl_01",
  "action": "PUT",
  "destination": "REFRIGERATOR"
}

The semantic representation should be independent of language.

18. ROUTINES
Routines are a first-class feature.
The elderly person may have repeated household routines.
Examples:
🌅 Morning

• Open living room window
• Bring water
• Bring medicine
• Prepare breakfast
🌙 Night
• Close bedroom window
• Close living room window
• Turn off lights
• Prepare bed
The actual routines are configurable by the family.
A routine is essentially a collection of semantic intents.
For example:
json
{
  "name": "Morning",
  "steps": [
    {
      "object": "bedroom_window",
      "action": "OPEN"
    },
    {
      "object": "living_room_window",
      "action": "OPEN"
    }
  ]
}

The user should be able to tap:
🌅 Morning
and see a sequence of simple requests.

25. FAMILY / ADMIN MODE

35. COLORS
Colors should have semantic consistency.
For example, the family could configure:
• Green = positive/action
• Red = stop/close
• Blue = objects
• Yellow = attention
• Purple = routines
But do not rely on color alone.
Every control must also have:
• image/icon
• spatial position
• optionally text
because elderly users may have difficulty distinguishing colors.
The exact color palette should be accessible and have sufficient contrast.

───

36. LARGE TOUCH TARGETS
Every interactive element must have a very large touch target.
Do not optimize for information density.
Optimize for:
"Can an elderly person with poor precision hit this button?"
Prefer a small number of huge cards over many small controls.
Avoid:
• tiny icons
• tiny X buttons
• tiny back arrows
• small checkboxes
• tiny text links
• dense lists

───

37. NO SWIPE-DEPENDENT NAVIGATION
Do not make important navigation dependent on swiping.
Avoid requiring:
• swipe left
• swipe right
• pull down
• pinch
• long scrolling
The user should primarily:
look → recognize → tap

───

38. CONSISTENCY
The same location on screen should perform the same conceptual function whenever possible.
For example:
Bottom-left:
⬅️ Back
Bottom-right:
🏠 Home
Or another consistent layout.
Do not move navigation controls unpredictably between screens.

───

39. IMMEDIATE FEEDBACK
Every tap should produce obvious feedback.
Possible feedback:
• visual button enlargement
• pressed state
• short sound
• haptic feedback
• screen transition
The user needs to know:
"The tablet understood my tap."
This is especially important because the user may not understand touchscreen technology.

───

40. ERROR TOLERANCE
Assume accidental taps.
The application should be forgiving.
Avoid irreversible operations.
For ordinary request construction:
• Back should undo the current choice.
• Home should safely return home.
• The user should never become trapped.
For important actions, confirmation can be used.
But do not add confirmations everywhere.
If the user selects:
Bring me a bowl.
there should not be:
Are you sure?
unless there is a specific reason.

───

41. HOME BUTTON
There should always be an obvious way to return to the home screen.
Do not rely exclusively on Android system navigation.
The app should provide its own consistent navigation.

───

42. FULL-SCREEN / KIOSK-LIKE EXPERIENCE
The app should feel like a dedicated household device rather than an Android application.
Investigate an appropriate kiosk/full-screen approach.
The elderly user should ideally not encounter:
• Android notification shade
• random system settings
• accidental app switching
• irrelevant system UI
However, do not make development/debugging difficult.
Provide a development/debug mode for developers.

───

43. ORIENTATION
Design primarily for landscape tablet usage unless there is a strong reason to support portrait.
The UI should adapt reasonably to different tablet resolutions.
Avoid hardcoded pixel coordinates.
Use responsive layouts.

───

44. ACCESSIBILITY
Although this is primarily a visual system, implement accessibility principles:
• very large text
• strong contrast
• large touch targets
• clear visual hierarchy
• no color-only meaning
• optional audio feedback
• optional TTS
• predictable navigation
• no unnecessary animations
• avoid flashing or distracting effects
The user may have:
• reduced vision
• reduced dexterity
• slower reaction time
• difficulty reading
• difficulty understanding abstract UI
• difficulty remembering navigation
Design accordingly.

───

45. ANIMATIONS
Use animations sparingly.
Animations should communicate:
• transition
• selection
• confirmation
They should not exist just because an app normally has animations.
Do not make the interface visually busy.

───

• accounts

Because this app may contain:

keep data local by default.

64. IMPORTANT PRODUCT RULE
Whenever you have a design decision, ask:
"Would this make sense to someone who has never used a computer?"
If the answer is no, simplify it.
If the user needs instructions such as:
"Press the menu button and then select..."
the design is probably wrong.
The ideal interaction is:
See something familiar → tap it → see the next obvious choice → tap it → show the result.

───

65. FINAL SUCCESS CRITERIA
The project is successful when an elderly person with essentially no technology experience can:
1. Pick up the tablet.
2. Recognize the things on screen.
3. Find a common request.
4. Construct a new request from pictures.
5. Understand what the final screen means.
6. Show that screen to the caregiver.
7. Return home without assistance.
8. Repeat the process later without being taught again.
The application should feel less like "using an app" and more like:
Pointing at pictures to tell another person what I need.
That is the product.
